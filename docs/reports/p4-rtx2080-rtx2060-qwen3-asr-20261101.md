# Tesla P4 vs RTX 2080 vs RTX 2060 for short Qwen3-ASR dictation

目前決策以[四卡效能、runtime 穩定性與易用性比較](qwen3-asr-four-gpu-runtime-20261101.md)為準；本篇保留 NVIDIA 規格來源。使用者已限定 RTX 2060 僅比較 6GB。

本次四卡更新位於 `perf/qwen3-asr-four-gpu-runtime`；下列原始分支為其基準。

Branch: `perf/p4-qwen3-asr-dictation-latency`. Development record: [Issue #12](https://github.com/DF-wu/CapsWriter-Offline-Container/issues/12). Existing application and runtime baseline: [P4 source audit and research](tesla-p4-qwen3-asr-runtime-20261031.md).

Research date: 2026-11-01. Scope: Qwen3-ASR 1.7B Q5_K, one user, short dictation, key-release to final-text latency. Desktop RTX 2080 means the original model, **not SUPER or Ti**; RTX 2060 means **6GB only**. This is a primary-source hardware comparison, not a benchmark. No runtime, deployment, or GPU settings were changed.

## Hardware facts

| Specification | Tesla P4 | RTX 2080 reference (Founders Edition where different) | RTX 2060 6GB |
| --- | --- | --- | --- |
| Architecture | Pascal | Turing | Turing |
| VRAM | 8 GB | 8 GB GDDR6 | 6 GB GDDR6 |
| Memory bandwidth | 192 GB/s | 448 GB/s | 336 GB/s |
| Peak FP32 | 5.5 TFLOPS, NVIDIA rating | ~10.07 TFLOPS (~10.60 FE), calculated below | ~6.45 TFLOPS, calculated |
| Board power rating | 75 W maximum; earlier sheet lists 50/75 W configurations | 215 W reference / 225 W FE | 160 W |
| CUDA compute capability | 6.1 | 7.5 | 7.5 |
| Tensor Cores | None | 368, Turing generation | 240, Turing generation |

Sources: P4 specifications [N1]; original RTX 2080, including reference/FE distinctions and P4 Tensor comparison [N2]; RTX 2060 variant specifications [N3], original 2060 Tensor count [N4]; compute capability [N5–N6]. These are rated ceilings/configurations, not sustained clocks, dictation power consumption, or workload measurements. NVIDIA's current comparison page [N7] uses the RTX 2080 FE values (1.80 GHz, 225 W), so mixing its power with reference clocks would describe different board configurations.

**Calculated FP32, not measured:** `CUDA cores × boost GHz × 2` gives RTX 2080 `2944 × 1.710 × 2 / 1000 = 10.06848 TFLOPS` (FE at 1.800 GHz: 10.5984) and RTX 2060 6GB `1920 × 1.680 × 2 / 1000 = 6.4512`. NVIDIA's Turing whitepaper rounds the original RTX 2080 reference figure to 10 TFLOPS [N2]. The calculation counts multiply and add separately; it is not quantized-inference throughput. Core counts/clocks come from [N2–N4].

## Ratios: specifications only, NOT benchmark speedups

- RTX 2080/P4: bandwidth `448/192 = 2.33×`; calculated-reference FP32/rated-P4 FP32 `10.06848/5.5 = 1.83×`; equal advertised VRAM capacity.
- RTX 2060 6GB/P4: bandwidth `336/192 = 1.75×`; FP32 `6.4512/5.5 = 1.17×`; VRAM `6/8 = 0.75×`.
- RTX 2080/RTX 2060 6GB: bandwidth `448/336 = 1.33×`; FP32 `10.06848/6.4512 = 1.56×`; VRAM `8/6 = 1.33×`.

The P4's advertised 22 INT8 TOPS [N1] and Turing Tensor TOPS [N2] use different execution paths from general FP32. None establishes Q5_K execution throughput. Q5_K does not itself prove use of INT8/INT4 Tensor instructions; the selected backend, kernels, shapes, and conversions determine actual acceleration. Tensor hardware availability alone does not prove that this application's current path uses it.

## Current runtime compatibility, narrowly checked

- **vLLM:** the fetched current GPU installation documentation requires NVIDIA compute capability **7.5 or higher**, and describes precompiled CUDA 12.9 binaries [R1]. P4 (6.1) is below that supported floor. RTX 2080 and RTX 2060 6GB meet the hardware floor. This is not verification of Qwen3-ASR support, Q5_K loading, the required attention/quantization kernels, VRAM sufficiency, or compatibility with the installed driver/package versions.
- **TensorRT:** NVIDIA's fetched current support matrix identifies **TensorRT 11.4.1** as latest and explicitly requires **SM 7.5 or higher** [R2]. P4 is excluded; these Turing cards meet the stated architecture floor. Historical P4 TensorRT support in its old datasheet [N1] must not be presented as support in the current release. Meeting the floor does not supply a Qwen3-ASR engine or a Q5_K conversion path, or establish TensorRT-LLM support. No installation or conversion was attempted.

These are compatibility boundaries for the fetched current documentation, not a proposal to replace the existing runtime. Older pinned stacks and the application's actual backend need separate checks; no exhaustive runtime survey was performed.

## Practical inference for release-to-final-text latency

The application's configured NVIDIA default is an ONNX CUDA encoder plus a Vulkan GGUF decoder, as established in the linked baseline report; deployed effective backends have not been observed. The encoder selects FP16 versus FP32 inputs from the loaded ONNX input type, not from the presence of Tensor Cores ([encoder source](https://github.com/DF-wu/CapsWriter-Offline-Container/blob/a674e40cb58c5c51991b0e20600a575b7db27944/core/server/engines/qwen_asr_gguf/inference/encoder.py)). Do not apply theoretical Turing Tensor throughput directly to this current pipeline or assume that replacing the card automatically changes the backend.

**Inference, unmeasured:** provided the whole workload fits in VRAM, stays on the GPU, and uses comparable working kernels, the original RTX 2080 is the strongest latency candidate of the three main cards: it combines the highest bandwidth and FP32 ceiling with Tensor hardware and 8 GB capacity. RTX 2060 6GB also has more bandwidth than P4 and Turing execution options, but its smaller memory capacity could force less offload or constrain buffers. P4 retains a materially lower board-power rating and 8 GB capacity, but lacks Tensor Cores and falls below the two current runtime floors checked above. These facts support candidate selection, not a guaranteed ordering of measured end-to-end latency.

Do not estimate total VRAM from “1.7B × five bits”: mixed tensor types, quantization metadata, audio encoder/activations, decoder state, workspaces, and runtime allocations also matter. No model-fit claim was verified in this research.

For a short utterance, release-to-final-text can include capture finalization, endpoint/silence waits, queue/transport, audio preprocessing, encoder/prefill work, autoregressive decoding, and text delivery. The parent code investigation must establish which stages actually lie after release, whether work already runs during recording, and which stages use GPU acceleration. Higher GPU throughput only reduces the accelerated portion. Even under a hypothetical stage speedup `r`, an unchanged fixed portion `F` and GPU portion `G` give `T_new = F + G/r`; inserting bandwidth or FP32 ratios as `r` is not justified here. Single-user final-text latency is not server batch throughput or time to first token.

A defensible comparison would keep audio, model artifact, backend/build, offload, decoding settings, and host path constant; distinguish cold from warmed operation; and record release-to-final plus stage timings and VRAM residency. No benchmark was run, no millisecond estimate or speed range is asserted, and the P4 datasheet's old image-inference marketing speedups are not evidence for this ASR workload.
