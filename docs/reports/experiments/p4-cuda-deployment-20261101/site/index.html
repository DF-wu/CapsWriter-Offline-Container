這次做了哪些修改

對準 P4 的 decoder 核心

固定 b7798 原始碼與 SHA-256，使用 CUDA 11.8 編譯 SM61 核心；在免洗容器內完成。以可重定位的 $ORIGIN 載入相依函式庫，移出編譯容器仍能運行。

啟動時確認真的使用 CUDA

偵測 NVIDIA 與內建 runtime 後選擇 CUDA，檢查 CUDA0 註冊；選定 CUDA 後若載入失敗，停止啟動，交由部署流程回復。CPU、Vulkan 與低顯存 preset 保留。

可驗證的權重與部署

沿用原模型，三份權重雜湊完全相同。runtime 壓縮包與每份函式庫均驗證雜湊，沿用原有 staging 與原子切換流程。

保存 Portainer 注入設定

以同一 CapsWriter 容器 ID 套用已測試的程式與函式庫，再重啟。核對 Config、HostConfig、網路設定指紋與應用設定；Immich 也以原 ID 恢復。

品質驗證如何判讀

在獨立免洗容器中，分別使用原 runtime 的 CPU decoder 與新 CUDA decoder，以相同參數、相同權重、temperature=0 的 greedy 解碼測試 5 份完整音訊。正規化後文字 5 / 5 相同，涵蓋英文、中文與語言混合。

HTTP 的 temperature 限制已分開記錄舊 HTTP 路徑接受 temperature 欄位，但 worker 呼叫 decode_stream 時仍使用 0.4。即使請求傳 0，文字也有隨機變動。因此 HTTP 測延遲、greedy 引擎測輸出一致性；本次未修改這段既有行為。這五份音訊是回歸檢查，不能證明所有場景零品質差異。

取捨與邊界

這個方案的優點

已在這張 P4 上實測；沿用現有模型與 ctypes 介面；省去重新轉換或下載另一份量化權重。相較原先只枚舉到 CPU 的 decoder，GPU 能實際承擔模型、KV 與 compute buffer。

需要留意的成本

本輪熱推論的整卡顯存觀測中位數由 1249 MiB 增至 2987 MiB。與 Immich 同時工作時可能競爭顯存、算力與散熱。已恢復 Immich 並做一筆共存辨識，但未進行 Immich 滿載壓力測試。

restart 已保留；recreate 必須使用新版映像目前是在原容器的 writable layer 套用更新，普通 restart 會保留。若 Portainer 從舊映像重建容器，更新會消失。分支中的 Dockerfile 已整合完整建置流程，但尚未合併 master、尚未替換 GHCR latest。回復資料保留在本機私人目錄。
